# 记忆策展 Agent 分阶段需求规格

- **日期：** 2026-05-22
- **主题：** 将 `docs/project-development.md` 收敛为可执行的产品需求与阶段路线图
- **范围：** Electron 桌面端，本地优先，个人长期记录与 Agent 辅助策展

---

## 1. 产品目标

记忆策展 Agent 是一个面向个人长期记录与回顾的本地优先桌面应用。它不是单纯的笔记归档工具，也不是一次性摘要工具，而是围绕用户每天产生的计划、笔记、日记、聊天素材、截图文字和主观感受，形成可持续整理、回顾、命名、关联和追踪的个人记忆工作台。

产品需要支持三种核心节奏：

1. **日输入：** 用户每天快速记录 todo、自由笔记、日记和外部文本素材。
2. **周整理：** 系统按周整理日常输入，形成具有复盘价值的结构化回顾。
3. **长期追踪：** 系统从连续记录中提炼长期主题、变化轨迹、重复模式和关键记忆片段。

MVP 的目标不是一次完成所有 Agent 能力，而是先建立稳定的数据底座、输入流程、日视图和基础归类能力，为后续周度策展与长期主题追踪提供可靠材料。

---

## 2. 目标用户

### 2.1 稳定记录但缺少回顾的人

用户已经有计划、随记或日记习惯，但内容分散，长期难以回看。系统需要把素材按时间和类型组织起来，让记录从堆积变成可复盘资产。

### 2.2 需要统一管理个人输入的人

用户会同时产生 todo、笔记、日记、聊天片段、截图文字等输入。系统需要提供统一入口，并把不同来源的文本归入日视图和记忆体系。

### 2.3 需要提炼人生素材的人

用户关注记录背后的主题、情绪变化、行为模式和叙事线索。系统需要帮助他们把零散内容提升为可命名、可追踪、可回看的长期主题和记忆节点。

---

## 3. 非目标

1. **不做团队协作工具。** 不支持多人任务分配、团队看板、权限协作或组织级知识库。
2. **不做纯归档型笔记系统。** 搜索和保存只是基础能力，核心价值是整理、命名、关联和追踪。
3. **不做单次摘要工具。** 单次总结不是主要价值，系统强调长期连续输入后的周期回顾和主题沉淀。
4. **不替代心理咨询。** 系统可以帮助观察感受、模式与冲突，但不提供诊断结论或医疗建议。
5. **MVP 不做复杂富文本。** 早期以纯文本和 Markdown 为主，不引入重型编辑器。

---

## 4. 核心信息模型

### 4.1 Todo

Todo 表示用户当天计划或执行事项，面向行动管理。它需要包含标题、日期、完成状态、创建时间、更新时间和可选备注。

### 4.2 Note

Note 表示自由笔记、事实记录、临时想法、素材片段或未整理内容。它偏向素材捕捉，需要保留原文和来源信息。

### 4.3 Journal

Journal 表示更主观、更完整的日记表达，包括感受、反思、总结、困惑和自我观察。日记需要保留完整原文，不能只保存摘要。

### 4.4 InputItem

InputItem 表示用户一次输入的原始材料。它可以来自手动文本、聊天粘贴、截图识别文本或其他外部素材。Agent 归类前后都应保留原始输入，避免误分类导致信息丢失。

### 4.5 MemoryFragment

MemoryFragment 表示从记录中提炼出的重要记忆片段。它不是普通标签，而是值得用户之后回看的事件、感受、选择、转折或关键线索。

### 4.6 Theme

Theme 表示长期主题，如职业选择、创作方向、关系互动、生活习惯、情绪波动、决策模式或个人困惑。主题需要能关联多个日期、多个片段和多个记录来源。

### 4.7 WeeklyReview

WeeklyReview 表示一周维度的结构化回顾。它需要包含计划执行、事实记录、主观感受、重复主题、关键事件、延后事项和可继续追踪的记忆线索。

## 5. 功能分阶段路线图

### 5.1 第一阶段：MVP 可开发版

MVP 目标是建立可用的本地记录工作台。它必须覆盖日常输入和日视图闭环，并提供基础 Agent 归类能力。

MVP 功能范围：

1. 本地 SQLite 数据库与基础数据模型。
2. 文本输入入口，支持普通文本和聊天内容粘贴。
3. 每日 todo 的创建、查看、完成和取消完成。
4. 自由笔记的创建、查看和列表回看。
5. 日记条目的创建、查看和历史回看。
6. Today 当日计划视图，集中展示当天 todo、笔记、日记和输入素材。
7. 基础 LLM 输入归类，把输入建议归为 todo、note、journal、memory clue 或 theme clue。
8. 本地优先隐私边界，明确哪些内容会发送给模型。
9. 基础设置页，支持配置 OpenAI-compatible provider、API key 和模型名称。

MVP 不要求自动生成完整周报、长期主题图谱或复杂变化对比，但需要为这些能力保留数据结构和页面入口。

### 5.2 第二阶段：策展增强版

第二阶段目标是从日常记录进入周期复盘和主题沉淀。

第二阶段功能范围：

1. 周度策展，按周整理计划执行、重要事件、主观感受和重复主题。
2. 长期主题追踪，从历史输入中提炼并维护 Theme。
3. 记忆片段命名，把重要记录提炼成可识别的 MemoryFragment。
4. 记忆片段关联，展示片段与日期、主题、感受和事件的关系。
5. Agent 建议面板，展示可归档、可命名、可关联和可追踪的候选项。

### 5.3 第三阶段：深度洞察版

第三阶段目标是增强输入来源和长期洞察能力。

第三阶段功能范围：

1. 截图内容理解与文本提取，将截图识别结果转入输入归类流程。
2. 变化对比，对不同时期的计划执行、情绪状态、关注主题和叙事方式做比较。
3. 模式识别，发现重复出现的行为模式、情绪波动和决策倾向。
4. 冲突与未完成议题识别，发现计划与行动不一致、态度变化或长期未推进问题。
5. 记忆关联网络，帮助用户理解内容之间为什么有关，而不是制造标签堆积。

## 6. MVP 详细需求

### 6.1 输入管理

用户可以在统一输入区提交文本。输入区需要支持短句、长段文本和聊天记录粘贴。系统保存原始输入，并允许用户接受或调整 Agent 的归类建议。

输入归类结果至少包含：

1. 建议类型：todo、note、journal、memory clue、theme clue 或 unknown。
2. 置信度或明确程度描述。
3. 建议理由。
4. 可写入的结构化字段。

当 LLM 不可用、请求失败或输出校验失败时，系统必须保留原始输入，并允许用户手动选择类型。

### 6.2 每日记录

用户可以围绕某一天创建 todo、note 和 journal。系统必须清楚区分执行事项、素材记录和主观叙事，避免所有内容混入同一个列表。

每日记录要求：

1. Todo 支持未完成和已完成状态。
2. Note 支持按创建时间展示。
3. Journal 支持按日期展示完整内容。
4. 所有记录都绑定日期。
5. 所有记录都保留创建时间和更新时间。

### 6.3 Today 视图

Today 是 MVP 的主入口。用户进入应用后，应能快速理解当天计划、已记录事项、主观感受和待整理素材。

Today 视图至少包含：

1. 当日 todo 区。
2. 当日笔记区。
3. 当日日记区。
4. 统一输入区。
5. Agent 归类建议区。
6. 可切换日期的基础控件。

### 6.4 列表与历史查看

MVP 需要提供笔记列表和日记条目查看。列表不是复杂搜索系统，但必须支持用户回看历史记录。

基础能力：

1. Notes 页面按时间倒序展示自由笔记。
2. Journal 页面按时间倒序展示日记条目。
3. 用户可以从列表定位到记录详情。
4. 记录详情保留原始内容，不只显示摘要。

### 6.5 设置与隐私

系统处理个人长期记录，MVP 必须明确隐私边界。

设置能力：

1. 配置 LLM provider base URL。
2. 配置 API key。
3. 配置模型名称。
4. 显示 LLM 请求前将发送的文本范围。
5. 默认所有数据库内容保存在本地。

## 7. Agent 能力边界

### 7.1 MVP Agent 能力

MVP 的 Agent 只负责输入理解和归类建议，不负责替用户生成结论。

允许能力：

1. 判断输入更接近 todo、note、journal、memory clue 或 theme clue。
2. 从聊天粘贴内容中识别可能的待办和关键事件。
3. 给出归类理由。
4. 输出结构化 JSON，并通过 Zod 校验。

禁止能力：

1. 不自动删除或覆盖用户原文。
2. 不对用户做心理诊断。
3. 不在用户未确认时自动创建长期主题。
4. 不把低置信度结果写入最终结构化记录。

### 7.2 后续 Agent 能力

第二阶段和第三阶段逐步增加周度策展、长期主题发现、变化追踪、记忆命名、记忆关联、模式识别和冲突识别。所有高级能力都必须保持可追溯：每个结论都能回到具体记录来源。

---

## 8. UI 工作台要求

应用采用桌面端三栏工作台结构：

1. 左侧：日期导航、页面导航、长期主题和记忆入口。
2. 中间：Today、Notes、Journal、Weekly Review、Themes、Memories 等主内容。
3. 右侧：Agent 建议、输入归类、相关记忆、主题线索和隐私提示。

视觉规范：

1. 黑色主题，主色 `#000000`，次色 `#212121`。
2. 圆角统一为 `6px`。
3. 禁止使用渐变色。
4. 交互状态需要自然克制，避免生硬跳变。
5. 桌面优先，同时保证窗口较窄时布局不崩坏。

---

## 9. 技术约束

项目基于现有 Electron 技术栈推进：

1. Electron + electron-vite。
2. React + TypeScript。
3. Tailwind CSS。
4. SQLite + Drizzle ORM + better-sqlite3。
5. Zustand 管理轻量 UI 状态。
6. TanStack Query 管理异步数据状态。
7. Zod 校验 LLM 输出和 IPC 输入输出。
8. OpenAI-compatible LLM provider 抽象。
9. Vitest、Testing Library 和 Playwright 用于测试。

工程边界：

1. 数据库、文件系统、截图和 LLM 请求代理放在主进程。
2. 预加载层只暴露有限且类型明确的 IPC 能力。
3. 渲染层只处理 UI 和交互状态，不直接访问数据库和 API key。
4. LLM 输出必须先校验再写入数据库。

## 10. 验收标准

### 10.1 MVP 验收

MVP 完成时必须满足：

1. 用户可以创建并查看当天 todo、note 和 journal。
2. 用户可以在 Today 视图看到当天计划、笔记、日记和输入素材。
3. 用户可以查看历史笔记列表和历史日记条目。
4. 用户粘贴一段文本后，系统可以给出归类建议。
5. LLM 不可用时，用户仍可手动保存记录。
6. 所有记录默认保存在本地 SQLite。
7. LLM 请求前能明确看到将发送的内容范围。
8. 类型检查、构建和核心测试通过。

### 10.2 第二阶段验收

第二阶段完成时必须满足：

1. 用户可以生成一周维度的结构化回顾。
2. 周度回顾包含计划执行、重要事件、感受变化和重复主题。
3. 用户可以查看长期主题及其关联记录。
4. 用户可以为重要记忆片段命名并查看关联来源。

### 10.3 第三阶段验收

第三阶段完成时必须满足：

1. 用户可以从截图或图片中提取文本并进入输入归类流程。
2. 用户可以对比不同时期的记录变化。
3. 系统可以识别重复模式，并展示对应记录来源。
4. 系统可以提示冲突和未完成议题，但不做诊断式判断。

## 11. 风险与控制

### 11.1 范围膨胀风险

完整愿景包含大量 Agent 能力。控制方式是严格把 MVP 限定为本地数据、日输入、Today 视图和基础归类。

### 11.2 LLM 输出不稳定风险

所有 LLM 输出必须通过 Zod schema 校验。校验失败时保留原始输入，并进入手动归类流程。

### 11.3 隐私风险

默认本地保存，LLM 请求前展示发送范围。API key 不进入渲染层，不写入日志。

### 11.4 记忆关联失真风险

高级 Agent 结论必须保留来源记录引用。系统不展示无法追溯的主题、模式或冲突结论。

---

## 12. 后续实施顺序建议

1. 建立数据库 schema、迁移和主进程数据服务。
2. 定义 preload IPC 契约和渲染层类型。
3. 实现 todo、note、journal 的本地 CRUD。
4. 实现 Today 视图与统一输入区。
5. 实现 LLM provider 配置和基础输入归类。
6. 实现 Notes 和 Journal 历史页面。
7. 补充 MVP 测试和端到端冒烟验证。

该顺序只作为后续 implementation plan 的输入，不在本需求规格中展开具体代码任务。
